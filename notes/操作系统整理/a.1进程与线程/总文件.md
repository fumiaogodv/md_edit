## 一、进程的概念、组成与特征

**进程与进程实体**
- 一个进程是动态的，不断变化的。
- 进程实体是静态的，类似于进程某一个瞬间的快照。
- 平时说的「那个进程」，实际上指的是进程实体，但两者差不多。

**本章思维导图涉及的主题**
进程的概念、组成、特征 → 进程的状态与转换 → 进程控制 → 进程通信 → 信号 → 线程。

## 二、进程的状态与转换

**主动阻塞与被动阻塞的区别**

从运行态到阻塞态，是「主动停止」，这里的主动含义是：进程只有在获得资源之后才可以继续，所以它主动选择阻塞来等待。这种「没有资源、被停止」叫做主动。

类似的，被动指的是：程序还在正常运行，这时一个优先级更高的程序要运行，系统把它停止了。这种「有资源却不能运行」叫做被动。

**进程控制为什么不能中断**

程序进行状态切换要做两件事情：
1. 身份的改变：state 改变。
2. 物理指针的改变：让新队列指向它，它自己也指向别的 PCB。

如果这两步做了一半就被中断，就会造成诸多混乱，所以进程控制必须保证原子性。

**实现原子的逻辑**
把希望不被打断的程序，放在关中断和开中断之间，这样程序的运行就不会被打断。

**关中断与开中断**
关中断和开中断是特权指令，用户程序不能使用。如果让用户程序用了，那病毒和流氓软件就无敌了。

**原语与作业调度**
- 创建一个新进程，就需要用到原语。
- 这里的作业调度，指的是把程序从外存放入内存。

**运行环境的保存**
下面例子里说的运行环境，指的是：先把进程运行的一些数据保存到 PCB 里，方便下一次再转为运行态的时候，从中断的指令处无缝衔接。

## 三、进程通信

**为什么需要进程通信**
各个进程不能随意访问别的进程的数据，否则安全性就崩了。

**解决办法**
划一片公共的区域，然后通过映射的方式，让另一个进程访问特定的数据。因为不能两个进程同时对这个共享区域进行写，所以要加上 PV 锁（信号量）。

**共享存储区的两种结构**
1. 基于数据结构的共享。
2. 基于存储区的共享。

**消息传递：直接通信方式**

流程：
1. 先确定一个初步印象：每一个进程的 PCB 都放在内核里，由内核统一管理。
2. 进程 P 在它的内存里写好消息头，也就是自己的 ID、接收进程的 ID 等信息。
3. 进程 P 使用 send 原语让内核执行，内核就把刚刚那个消息放到进程 Q 的 PCB 的消息队列里。
4. 进程 Q 使用接收原语，让内核把消息发送给它，它就可以在自己的内存里编辑、使用这个消息。

**消息传递：间接通信方式（信箱）**

流程和直接通信十分相似，只是把接收方变成了一个抽象的集合，形成了「一 — 多 — 一」的结构：
1. 消息头写的不是接收方的 PID，而是邮箱的信息。
2. 一样使用原语把数据发送给内核，但这里数据不是放在另一个进程的 PCB 后面，而是一个抽象的空间。
3. 任何一个接收方都可以使用接收原语，往这个信箱获取数据。

**管道通信的特点**
1. 是半双工通信，只能单向传输。而且只要一个管道建立了，它就只有一个流向，要么从 A 到 B，要么从 B 到 A。
2. 管道的数据结构类似于循环队列。
3. 管道允许多个写进程、一个读进程。

## 四、信号（Signal）机制

- 收到信号的进程，不知道发送者是谁。
- 进程之间能发送的信号是有限制的；而内核发送的信号没有限制。
- 一个进程什么时候处理收到的信号：当这个进程从内核态转为用户态的时候，也就是当运行了 trap 或者 IO 操作的时候。这时候先进入内核态再出来，就会统一检查一次。选这个时机，是因为数据都在 PCB 里保存好了，就是在要继续运行之前顺便检查一次。
- 如何判断哪些信号要处理：需要两个表。一个是阻塞信号表，用来表示有一些信号即使收到了也不能执行；另一个是待处理信号表，放要处理的信号。过程是：待处理信号的每一位，和「取反操作后的阻塞信号」进行与运算，得出的结果为 1 的信号就执行。
- 怎么处理信号：为每一个信号都写一个处理程序，发生的时候自动执行。用户可以自定义很多处理信号的执行程序，但有一些特别核心的信号，比如 kill -9，不能自定义。
- 一句话理解：信号就是对一些异常处理的默认做法，加上了个性化的实现。

## 五、线程

### 用户级线程

1. 线程的管理由每一个进程的线程库管理。
2. CPU 不需要变态（不需要切换到内核态）。
3. 内核意识不到线程的存在，只是认为它是一个进程。

优点：不需要变态，开销小，效率高。

缺点：
1. 一个线程阻塞了，整个程序就不能运行了，并发性不好。
2. 不能在多核 CPU 上同时执行，并行性不好。

### 内核级线程

1. 内核级线程的管理工作由操作系统内核完成。
2. 线程调度、切换等工作都由内核负责，因此内核级线程的切换必然需要在核心态下才能完成。
3. 操作系统会为每个内核级线程建立相应的 TCB（线程控制块），通过 TCB 对线程进行管理。内核级线程，就是从操作系统内核视角看能看到的线程。

优点：当一个线程被阻塞后，别的线程还可以继续执行，并发能力强；多线程可在多核处理机上并行执行。

缺点：一个用户进程会占用多个内核级线程，线程切换由操作系统内核完成，需要切换到核心态，因此线程管理的成本高，开销大。

### 对比小结

| 维度 | 用户级线程 | 内核级线程 |
|---|---|---|
| 管理者 | 用户空间的线程库 | 操作系统内核 |
| 是否需要变态 | 不需要 | 需要（核心态） |
| 并发/并行能力 | 弱（一个阻塞全阻塞，不能多核并行） | 强（可多核并行） |
| 开销 | 小 | 大 |

TCB 和进程的 PCB 基本一样，放一些存储的数据信息，以便在中止后再次运行。

## 六、CPU 调度

### 进程与线程的地位

- 不支持内核级线程的操作系统：进程是资源分配的基本单位，也是调度的基本单位。
- 支持内核级线程的操作系统：进程是资源分配的基本单位，线程是调度的基本单位。

### 调度器（调度程序）

调度器决定了：一是调度算法，二是每一个进程的运行时间。

会触发调度程序的事件有四个：
1. 创建新进程。
2. 进程退出。
3. 运行进程阻塞。
4. IO 中断发生。

### 各种调度算法的特点

**时间片轮转算法**
1. 规定一个时间片，然后按照时间片来让程序执行。
2. 假如时间片是 2，第二个程序的到达时间也是 2，那就是第一个运行两秒，然后回到队列排队。
3. 也就是在「按固定时间排队」的基础上，还考虑了到达时间不同的情况。

**非抢占式优先级调度算法**
1. 每一个程序运行完之后，再看是否有高优先级的进程存在。
2. 存在就让它运行。

**抢占式优先级调度算法**
1. 在每一个进程到达的时候，检查自己是否是高优先级的进程。

**多级反馈队列调度算法**
1. 有多个队列，低优先级队列的时间片小。
2. 类似于时间片轮转算法，不同的是，每一个进程运行完会跑到第二级等待。
3. 只有低优先级队列为空，才可以运行高优先级的；被抢占的进程会在原地等着。

**本章思维导图涉及的主题**
调度的概念层次 → 进程调度的时机、切换与过程、方式 → 调度器和闲逛进程 → 调度算法的评价指标 → 各种调度算法 → 多处理机调度。

### 评价指标

响应比 = （等待时间 + 运行时间）÷ 运行时间。

### p操作伪代码

```
void wait(semaphore S) {
    // 1. 底层锁保护（如：关中断/自旋锁），保证下面操作的原子性
    acquire_hardware_lock(); 

    S.value--;           // 只要调用 P，资源计数器立刻减 1

    if (S.value < 0) {   // 减完后如果小于 0，说明刚才资源已经空了，现在倒欠了
        
        // a. 把当前正在运行的进程（current）拿到，挂到该信号量的等待队列 L 中
        add_to_queue(S.L, current_process); 
        
        // b. 调用操作系统的阻塞原语，将当前进程状态改为“阻塞态”，主动让出 CPU
        // 【注意】：block 内部会安全地释放底层的硬件锁，让别人能继续调用 P/V
        block(S.L);      
        
        return;          // 进程在这里“睡着”了，后面的代码暂时不会执行
    }

    // 2. 如果没进 if，说明资源足够，解开底层锁，进程顺利通过，进入临界区
    release_hardware_lock(); 
}

void signal(semaphore S) {
    // 1. 底层锁保护，保证下面操作的原子性
    acquire_hardware_lock(); 

    S.value++;           // 只要调用 V，资源计数器立刻加 1

    if (S.value <= 0) {  // 加完后如果依然 <= 0，说明队列里【至少还有一个】在睡觉的进程
        
        // a. 从等待队列 L 中强行拉出一个（通常是 FIFO，排在最前面的）进程
        process *p = remove_from_queue(S.L); 
        
        // b. 调用操作系统的唤醒原语，把这个进程的状态改为“就绪态”，丢进就绪队列排队
        wakeup(p);       
    }

    // 2. 解开底层锁，当前进程继续执行自己后面的代码
    release_hardware_lock(); 
}
```

## 九、死锁的预防与处理策略

死锁的发生必须同时满足四个必要条件。**死锁预防（Deadlock Prevention）**的策略就是在系统设计阶段设置严格的限制，通过**破坏这四个必要条件中的任意一个**来杜绝死锁。

------

**1. 破坏互斥条件**

- **具体措施**：把原本只能独占使用的**互斥资源**改造成可以供多个进程**共享使用**的资源。
- **经典实现（SPOOLing 技术）**：
- 例如**打印机**是典型的独占设备。系统引入 SPOOLing 技术（假脱机技术），在磁盘上开辟缓冲区。
- 多个进程发起打印请求时，并不直接占用物理打印机，而是把数据写入磁盘输出井；由系统后台守护进程排队打印。在各进程看来，打印机变成了“共享”设备。
- **缺点/局限**：许多物理资源（如临界区内存、磁带机、修改同一个文件）在逻辑上必须严格互斥，无法全部改造成共享资源。

------

**2. 破坏不剥夺条件（不可抢占条件）**

- **具体措施**：允许强行剥夺其他进程已占有的资源。有两种常见方案：
- **方案一（主动释放）**：一个进程占有了某些资源，在申请新资源得不到满足而被迫等待时，**必须主动释放自己当前占有的所有资源**，待以后需要时再重新申请。
- **方案二（系统强行剥夺）**：当进程 A 申请的资源被进程 B 占用时，如果进程 B 当前也处于等待状态，系统可以**强行剥夺 B 的资源分配给 A**（通常结合进程优先级）。
- **缺点/局限**：
- 实现极其复杂，需要频繁保存和恢复现场（如 CPU 寄存器、内存状态）。
- 如果反复申请、释放资源，会导致进程运行效率低下甚至引发**饥饿（Starvation）**。

------

**3. 破坏请求和保持条件**

- **具体措施**：采用**静态资源分配法**或**分阶段释放申请法**，杜绝“吃着碗里的，看着锅里的”。
- **静态分配（一次性分配）**：进程在运行之前，必须**一次性申请其整个生命周期所需的全部资源**。只要有一种资源无法满足，系统就不给它分配任何资源，该进程暂不投入运行。
- **先释放再申请**：允许进程只申请初期所需资源，但在申请下一阶段的新资源前，必须**先释放当前占用的全部资源**。
- **缺点/局限**：
- **资源利用率极低**：某些资源可能只在进程结束前用一瞬间，但整个运行期都被提前霸占。
- **容易导致饥饿**：需要资源多的进程可能长时间无法凑齐全部资源，一直无法启动。

------

**4. 破坏循环等待条件**

- **具体措施**：采用**顺序资源分配法（资源按序编号）**。
- 系统给所有资源赋予一个全局唯一的整数编号（如：输入机=1，打印机=2，磁盘=3）。
- 规定所有进程必须**严格按照编号递增的顺序**申请资源。
- 进程已持有编号为 N 的资源时，后续只能申请编号 >N 的资源；若想申请编号

| 策略分类                  | 核心思想                                                     | 时机与机制                                                   | 代表算法 / 措施                                              |
| ------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **死锁预防 (Prevention)** | **静态约束**：通过人为施加死板的规则，**直接破坏死锁的 4 个必要条件之一**，让死锁从物理/逻辑上根本不可能产生。 | **事前静态限制**（规则写死在系统设计或编程规范中）           | **资源有序分配算法**（破循环等待）、**静态一次性分配**（破请求和保持）、**SPOOLing**（破互斥）、**主动释放**（破不剥夺） |
| **死锁避免 (Avoidance)**  | **动态评估**：不破坏 4 个必要条件，允许进程自由申请资源，但在**每次分配前进行动态安全性计算**，只要会导致“不安全状态”就暂缓分配。 | **运行时动态预判**（走一步算一步，确保系统始终处于安全状态） | **银行家算法 (A)**、**系统安全状态判定**                     |
| **死锁检测 (Detection)**  | **事后排查**：平时对资源申请不加任何限制，允许死锁发生；系统定期运行检测算法，找出当前已经陷入死锁的进程。 | **事后检查**                                                 | **资源分配图化简法 (D)**、死锁定理                           |
| **死锁解除 (Recovery)**   | **事后补救**：检测出死锁后，采取措施打破死锁。               | **事后处置**                                                 | 资源剥夺法、撤销进程法（终止进程）、进程回退法               |

## 不同条件造成的唤醒，阻塞等
| 事件类型                                     | 进程状态变化        | 属于什么操作？          |
| ---------------------------------------- | ------------- | ---------------- |
| **等待的任何外部事件完成**（I/O、磁盘装页、网络数据到）          | 阻塞态 $\to$ 就绪态 | **唤醒 (Wakeup)**  |
| **等待的任何同步资源到位**（锁释放、信号量 V 操作、消息到达、子进程退出） | 阻塞态 $\to$ 就绪态 | **唤醒 (Wakeup)**  |
| **倒计时结束**（睡眠时间到）                         | 阻塞态 $\to$ 就绪态 | **唤醒 (Wakeup)**  |
| **运行态进程时间片用完**                           | 运行态 $\to$ 就绪态 | **抢占/调度（非唤醒）**   |
| **运行态进程主动请求资源/等待事件**                     | 运行态 $\to$ 阻塞态 | **阻塞/挂起（Block）** |
