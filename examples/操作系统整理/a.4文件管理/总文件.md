# 文件管理 · 总文件

## 一、FCB和文件和文件夹

在**传统 FCB（文件控制块）模型**下，文件、文件夹与 FCB 的关系可以总结为一句话：**“FCB 是文件的元数据结构；文件夹本质是特殊文件，其数据内容就是一张存满子文件 FCB 的表格。”**
### 1. 三者的各自定位
* **FCB（文件控制块）**：
* 操作系统的元数据结构。
* **一条 FCB 对应一个文件（或文件夹）**，完整记录该文件的属性（文件名、物理块号、大小、权限等）。
* **普通文件**：
* **FCB**：存放在其所在父目录的数据块中。
* **数据区**：存放用户实际的文本、代码、二进制数据等。
* **文件夹（目录文件）**：
* **自身的 FCB**：存放在其父目录的数据块中（用来标记这个文件夹自身的名字和存放位置）。
* **自身的数据区**：**一个定长的 `FCB 结构体数组**`，数组里的每一项就是该目录下某个子文件或子目录的完整 FCB。
---
### 2. 三者的包含与引用关系
```text
[父目录的数据区]
  └── FCB（文件夹 "docs"）：{ 名称: "docs", 属性: 目录, 物理块: 块 50 }
                                │
                                ▼ （读取磁盘块 50）
[文件夹 "docs" 的数据区（本质是 FCB 数组）]
  ├── FCB 1: { 名称: ".", 属性: 目录, 物理块: 块 50 }          <-- 指向自己
  ├── FCB 2: { 名称: "..", 属性: 目录, 物理块: 父目录块号 }     <-- 指向父目录
  ├── FCB 3: { 名称: "a.txt", 属性: 文件, 物理块: 块 101... }  <-- 子文件 a.txt 的完整 FCB
  └── FCB 4: { 名称: "work", 属性: 目录, 物理块: 块 80... }   <-- 子目录 work 的完整 FCB
                                │
                                ▼ （通过 FCB 3 的物理块号读取）
[文件 "a.txt" 的数据区]
  └── 实际文本内容（"Hello World..."）
```
---
### 3. 核心行为运作逻辑
* **创建文件**：
在当前目录的数据块中，找一个空闲的 FCB 槽位，把新文件的名字、大小、分配的物理盘块号直接填入该 FCB。
* **向文件夹放入文件**：
在目标文件夹的数据块内，追加写入一条该新文件的完整 FCB 记录。
* **按路径查找文件（如 `/docs/a.txt`）**：
1. 读根目录盘块，遍历内部的 FCB 数组，按名字匹配找到 `docs` 的 FCB，获取其数据区物理盘块号（块 50）。
2. 读磁盘块 50（即 `docs` 目录的数据区），遍历内部的 FCB 数组，按名字匹配找到 `a.txt` 的 FCB。
3. 从 `a.txt` 的 FCB 中读出物理盘块号（块 101），完成数据定位。

## 二、目录和索引节点（Inode）管理文件系统

### 1. 核心架构：名字与本体彻底分离
整个文件系统的逻辑结构建立在 **“目录只管导航，Inode 才是档案本体”** 的分工之上：
* **目录文件（Navigation Layer）**：
* 本质是一个普通文件，其数据块中维护着一张精简表格。
* **每条记录只存两项**：`文件/目录名` + `对应的 Inode 编号`。
* 不论是普通文件还是子文件夹，在父目录里都只体现为这样一行映射。
* **索引节点 Inode（Metadata & Pointer Layer）**：
* 文件的客观物理本体。
* **内部保存所有元数据与物理地址**：文件类型（普通/目录）、访问权限（`rwx`）、文件大小、硬链接计数、以及指向真实数据盘块的**直接/间接地址指针**。
---
### 2. 结构关系对照
```text
目录
│
├── a.txt ──→ Inode 101
│              ├── 类型：普通文件
│              ├── 权限：rw
│              └── 数据块地址 ──→ 文件数据
│
└── docs ───→ Inode 102
               ├── 类型：目录
               ├── 权限：rwx
               └── 数据块地址 ──→ 目录项
                                  ├── sub.c ──→ Inode 201
                                  └── ..    ──→ 上级目录 Inode
```
---
### 3. 三大核心推论
1. **路径解析是逐级递归的**：
* 从根目录 Inode 出发，读取目录数据块找到下一级的 Inode 编号；若是子目录，则继续读取其数据块向下检索，直到命中目标文件的 Inode。
2. **硬链接的本质**：
* 不同的目录项（甚至不同的目录）中写入了**相同的 Inode 编号**，共享同一份物理属性与数据块。
3. **安全与权限校验发生在 Inode**：
* 目录项只负责“按名找号”，真正的权限校验（能否读、写、执行）必须在打开对应 Inode 时由内核进行判定。



## 三、文件的逻辑结构与物理结构

### 一、文件的逻辑结构（程序员写的算法）

#### 1. 算法作用

它决定了**用户或应用程序在代码里如何组织和看待数据**。逻辑结构是为你读写业务数据服务的。

#### 2. 核心算法与数据结构

- **顺序文件算法：** 在代码里把数据写成固定长度的结构体（Record），第 1 条、第 2 条、第 3 条记录在逻辑上依次紧挨着。
    
- **索引文件算法：** 程序员在应用层自己维护一张索引表（如定长数组、B树）。查数据时，先用你的算法在索引表里做二分查找，找到对应的序号。
    
- **无结构文件算法：** 根本不分行，把文件看作一串连续的、没有规律的字节流（如 `.txt`、`.bin`）。
    

#### 3. 算法目标

**对应用层友好。** 追求的是：怎么让代码更好写？怎么能通过“学号”、“商品ID”等业务关键字最快锁定第几条数据？

### 二、文件的物理结构（OS 内核写的算法）

#### 1. 算法作用

它决定了**操作系统内核如何把文件塞进磁盘的一个个物理盘块（Sector/Block）中**。物理结构是为管理硬件服务的。

#### 2. 核心算法与数据结构

- **连续分配算法：** OS 在磁盘空闲块里找一段**完全连续的盘块**，把数据一股脑放进去。
    
- **链接分配算法：** OS 随便在磁盘各处找空闲块（不连续），然后在每个盘块的末尾加上一个指针，像拉手一样把它们串起来。
    
- **索引分配算法：** OS 专门在磁盘上申请一个**物理索引块**，里面塞满指针，按顺序指向这个文件占用的各个离散数据块。
    

#### 3. 算法目标

**对硬件和整体系统友好。** 追求的是：怎么减少磁盘碎片？怎么提高磁盘空间利用率？怎么减少磁头移动的开销？

### 三、两套隔离算法的本质区别（对比表）

|**维度**|**文件的逻辑结构算法（应用层/记录视角）**|**文件的物理结构算法（内核层/盘块视角）**|
|---|---|---|
|**管理者是谁**|**程序员 / 数据库引擎 / 应用程序**|**OS 文件系统内核 / 磁盘驱动程序**|
|**操作的基本单位**|**记录（Record）或字节（Byte）**|**磁盘块（Block，通常为 4 KB）**|
|**算法的出发点**|怎么方便人类按业务逻辑（如姓名）分类和检索|怎么把硬件磁盘的空间利用率压榨到极限|
|**两者的交集**|**无**。你写代码设计“逻辑索引文件”时，根本不用管这电脑装的是机械硬盘还是固态硬盘。|**无**。内核分配磁盘块时，根本不知道你这个块里存的是图片、视频还是文本。|

### 四、它们是如何发生交集的？（翻译官的作用）

既然完全没关系，数据怎么读出来？—— **靠 OS 在运行时，把逻辑请求“翻译”成物理命令。**

1. **你的代码（逻辑算法触发）：** “我要读这个文件的**第 3 条记录**。”
    
2. **OS 内核（翻译官介入）：**
    
    - OS 先根据你的逻辑结构，计算出第 3 条记录位于文件的**第 1 个逻辑块**（假设每条记录很长）。
        
    - 接着，OS 查自己维护的物理文件控制块（FCB/Inode），看这个文件的**第 1 个逻辑块对应的到底是哪个物理盘块**。
        
    - 如果物理上是**链接分配**，OS 就得顺着链表从第 0 块读到第 1 块；如果物理上是**索引分配**，OS 就直接去物理索引表里查第 1 项。
        
3. **驱动程序（物理算法执行）：** 拿着最终翻译出来的真实盘块号（比如：第 1025 号盘块），去通知磁盘磁头：“去把 1025 号盘块的数据读出来。”
    

#### 考研一句话记死

- **逻辑结构** 是你在代码里和数据玩的游戏，决定了数据在**用户眼中的排布**；
    
- **物理结构** 是 OS 和磁盘硬件玩的魔方，决定了数据在**磁盘上的实际安家方式**；
    
- 它们**各自独立、互不干扰**，你用什么逻辑结构，OS 物理上都能用任何一种分配方式帮你接盘并翻译。





## 四、顺序分配连接分配索引分配

| **分配方式**       | **How?**                                 | **目录项内容**                             | **优点**                              | **缺点**                                                   |
| -------------- | ---------------------------------------- | ------------------------------------- | ----------------------------------- | -------------------------------------------------------- |
| **顺序分配**       | 为文件分配的必须 是连续的磁盘块                         | 起始块号、文件长度                             | 顺序存取速度快，支持随机访问                      | 会产生碎片，不利于文件拓展                                            |
| **链接分配（隐式链接）** | 除文件的最后一个盘块之外，每个盘块中都存有指向下一个盘块的指针          | 起始块号、结束块号                             | 可解决碎片问题，外存利用率高，文件拓展实现方便             | 只能顺序访问，不能随机访问。                                           |
| **链接分配（显式链接）** | 建立一张文件分配表(FAT)，显式记录盘块的先后关系（开机后 FAT 常驻内存） | 起始块号                                  | 除了拥有隐式链接的优点之外，还可通过查询内存中的 FAT 实现随机访问 | FAT 需要占用一定的存储空间                                          |
| **索引分配**       | 为文件数据块建立索引表。若文件太大，可采用链接方案、多层索引、混合索引      | 链接方案记录的是第一个索引块的块号，多层/混合索引记录的是顶级索引块的块号 | 支持随机访问，易于实现文件的拓展                    | 索引表需占用一定的存储空间。访问数据块前需要先读入索引块。若采用链接方案，查找索引块时可能需要很多次读磁盘操作。 |



## 五、硬盘访问节点和内存访问节点
磁盘索引节点（Disk Inode）**与**内存索引节点（In-Core Inode / Memory Inode）**的区别，本质是**“静态持久化档案”**与**“动态运行时状态”的区别。
当文件静止在磁盘上时，它只有一个磁盘 Inode；当文件被某个进程通过 `open()` 打开时，操作系统会把磁盘 Inode 读入内存，并**动态追加大量内存管理专属的控制字段**，形成内存 Inode。

### 1. 核心区别对比
| 维度 | 磁盘索引节点 (Disk Inode) | 内存索引节点 (In-Core Inode) |
| --- | --- | --- |
| **存在位置** | 外存（磁盘的 Inode 区），永久保存 | 物理内存中，随开机关机或文件关闭而销毁 |
| **存在数量** | 系统中每个文件**必定且永久**对应一个 | 只有**当前被打开/正在使用**的文件才会在内存中创建 |
| **包含内容** | 仅包含文件的**静态元数据**（权限、大小、物理盘块等） | **包含磁盘 Inode 的全部内容** + **运行时动态控制信息** |
| **修改写回** | 只有修改了文件属性或内容后，才会由内存同步写回磁盘 | 频繁动态变化（如引用计数、状态锁、脏标记） |

### 2. 它们各自包含什么？
#### ① 磁盘索引节点包含的内容（静态数据）
* **文件主标识符**：文件所有者 ID（UID）、组 ID（GID）。
* **文件类型与存取权限**：普通文件/目录/设备文件、读写执行权限（rwx）。
* **文件物理大小**：文件的逻辑字节大小。
* **文件物理地址指针**：直接块号、一级间接块号、二级间接块号等（指向实际数据盘块）。
* **时间戳**：创建时间、最近访问时间、最近修改时间。
* **硬链接计数（Link Count）**：有多少个目录项（文件名）指向本 Inode。
---
#### ② 内存索引节点包含的内容（动态数据）
内存 Inode 是在磁盘 Inode 基础上的**超集**，除了复制磁盘 Inode 的所有内容外，还增加了以下关键字段：
* **Inode 编号（Inode Number）**：
* *注：磁盘 Inode 本身不存自己的编号（其编号是 Inode 表的数组下标），但加载到内存后必须显式记录该编号，以便快速匹配。*
* **设备号（Device ID）**：标识该文件来自哪块硬盘或分区。
* **状态标记（Status Flags）**：
* **锁定标志（Lock Flag）**：表示该 Inode 是否正在被某个进程修改，防止并发冲突。
* **脏标志（Dirty Flag / Modified）**：标记内存 Inode 是否被修改过。若为脏，关闭文件或 sync 时必须写回磁盘。
* **访问计数 / 引用计数（Reference Count / Count）**：
* 记录**当前有多少个进程或系统打开文件表项（File Table）正在使用这个 Inode**。
* 只有当引用计数降为 0 时，操作系统才会从内存中释放该内存 Inode。
* **同步互斥量 / 等待队列指针**：当多个进程排队等待使用该 Inode 时的阻塞等待队列。
* **挂载点指示（Mount Information）**：如果该目录被挂载了其他文件系统，记录其挂载信息。
---
### 3. 打开与关闭文件的生命周期联动
1. **打开文件 (`open`)**：
* 系统检索目录项拿到 Inode 编号。
* 检查内存中是否已有该 Inode：
* **若没有**：从磁盘读取该文件的磁盘 Inode，在内存中构建内存 Inode，**引用计数设为 1**。
* **若已有**：直接复用内存中的 Inode，**引用计数 +1**。
2. **读写文件 (`read / write`)**：
* 系统通过内存 Inode 里的直接/间接块指针快速做物理寻址，修改文件大小时将内存 Inode 标记为“脏（Dirty）”。
3. **关闭文件 (`close`)**：
* 内存 Inode 的**引用计数 -1**。
* 如果引用计数减到 0 且脏标志为真：操作系统将修改后的元数据**写回磁盘的 Inode 区**，然后释放这块内存 Inode 结构体。


## 六、文件大小和直接地址间接地址关系
### 1. Inode 和文件的关系
* **一个文件 ＝ 一个 Inode（档案袋）**。
* 不管文件多大多小，它永远只有一个 Inode。
---
### 2. 直接地址和间接地址的关系（怎么装下大文件）
* **直接地址 ＝ 直达车**：
* 指针直接指向装数据的文件块。
* **特点**：速度最快，但 Inode 空间有限，只能放几个指针，所以**只能装小文件**。
* **间接地址 ＝ 中转套娃（目录的目录）**：
* **一级间接**：指针不指数据，而是指向一个“中转块”，中转块里装满了指针，再指向数据（相当于建了个清单）。
* **二级间接**：指向“总清单”，总清单指向“分清单”，分清单才指向数据。
* **三级间接**：继续多套一层娃。
* **特点**：虽然读起来要多跑几趟（多耗费几次读盘），但能把指针数量**按指数级疯狂放大**。
---
### 3. 它们和“文件大小”的关系
* **小文件**：直接用 Inode 里的**直接地址**就够了，读取一步到位。
* **中等文件**：直接地址装不下了，启用**一级间接**来扩容。
* **超大文件**：一级也装不下了，启用**二级/三级间接**拼命套娃，从而让单个文件能支持到几 GB 甚至几 TB。


## 七、open和close操作的流程

### 在操作系统的文件管理中
文件的**打开操作（`open` 系统调用）**和**关闭操作（`close` 系统调用）**的主要目的，是**将耗时的磁盘检索工作在读写前一次性完成，并在内存中建立/清理运行时的控制结构**。
### 1. 打开文件操作（`open`）的主要工作
用户程序在读写文件前必须先执行 `open`，其核心任务是“将文件的元数据从外存载入内存，并建立多级打开文件表的映射关系”：
1. **目录检索与路径解析**：
* 根据传入的文件路径（如 `/home/user/test.txt`），从根目录或当前工作目录开始，逐级读取目录项，按文件名匹配找到目标文件的 FCB（或 Inode）。
2. **权限与访问控制检查**：
* 检查当前进程的用户权限与请求的打开模式（如只读、只写、追加等）是否匹配。
3. **维护内存索引节点（In-Core Inode）**：
* 检查该文件的 Inode 是否已在内存中。
* **若不在**：从磁盘读取该 Inode 写入内存，并初始化其访问计数（引用计数）为 1。
* **若已在**：直接复用该内存 Inode，并将其**访问计数（引用计数）加 1**。
4. **填写系统打开文件表（System-wide File Table）**：
* 在系统表中申请一个空闲表项，记录当前文件的打开模式、初始读写位置指针（offset，默认为 0）、共享计数，并设置指针指向内存 Inode。
5. **填写进程打开文件表（Per-process File Table）**：
* 在当前进程的打开文件表中分配一个空闲槽位，填入指向对应系统打开文件表项的指针。
6. **返回文件描述符（`fd`）**：
* 将进程表中的槽位下标（即 `fd`，如 3）返回给用户态程序。
* **后续的所有 `read` / `write` 操作直接带上 `fd` 即可，再也不需要重新走磁盘遍历目录解析路径**。
---
### 2. 关闭文件操作（`close`）的主要工作
当程序完成文件读写调用 `close(fd)` 时，其核心任务是“释放内存控制结构，并在必要时将修改同步写回磁盘”：
1. **清理进程打开文件表**：
* 释放该进程打开文件表中 `fd` 对应的槽位，解除与系统打开文件表项的关联（之后该 `fd` 失效并可被复用）。
2. **更新系统打开文件表**：
* 减少该系统表项的共享计数。若计数归零，则释放该系统表项。
3. **递减内存 Inode 的访问计数**：
* 将内存 Inode 的**访问计数（引用计数）减 1**。
4. **条件触发：写回磁盘与释放内存 Inode**：
* 如果该内存 Inode 的访问计数**降为 0**（说明全系统没有任何进程还在打开该文件）：
* **检查脏标志（Dirty Flag）**：如果文件内容或元数据被修改过，将内存中的最新数据和 Inode **写回磁盘**。
* **释放内存**：从内存中彻底注销并回收该内存 Inode 结构体。
---
### 总结对照
| 阶段 | 核心目标 | 对外存（磁盘）的操作 | 对内存结构的影响 |
| --- | --- | --- | --- |
| **打开 (`open`)** | 预热元数据，避免后续重复寻道查目录 | 读目录项 + 读磁盘 Inode | 建立 `进程表 -> 系统表 -> 内存 Inode` 的三级映射，引用计数 $+1$ |
| **关闭 (`close`)** | 释放内存资源，确保数据持久化落盘 | 若访问计数归零且为脏，则写回磁盘 Inode 与数据 | 销毁映射项，引用计数 $-1$，归零时回收内存 Inode |


## 八、read操作的流程

1. **查找目录项（定位文件）**：从上级目录的数据块中逐级匹配文件名，找到目标文件的 FCB 或 Inode 编号。
2. **检查合法性（权限与模式检查）**：核对当前进程的用户权限（rwx）与本次操作（如只读、只写）是否匹配。
3. **物理地址翻译（寻址）**：根据文件当前的读写指针（offset），结合内存 Inode 的物理地址指针，计算出目标数据所在的真实磁盘物理块号。
4. **I/O 操作（读取磁盘数据）**：
* 先检查内核缓冲区（Page Cache）：若命中则直接跳过。
* 若未命中，则**启动磁盘 I/O**，把磁盘物理块的数据读入内核缓冲区。
1. **数据拷贝与更新**：将内核缓冲区的数据拷贝到用户指定的内存空间，并自动累加文件的读写指针（offset）。

## 十、硬链接特点
### 一个文件A硬链接一个文件B

### 1. 硬链接的特点与物理地址关系
* **特点**：
* 文件 `a` 和文件 `b` 具有完全平等的地位，它们不是“主从”关系，而是同一个文件的两个不同名字。
* 修改 `a` 的内容，`b` 的内容会同步改变；修改 `a` 的权限，`b` 的权限也会改变。
* 删除 `a`，文件数据不会丢失，`b` 依然可以正常读写；只有当指向该文件的**所有硬链接全部被删除且没有进程打开它时**，文件占用的磁盘物理块才会被真正释放。
* **物理地址**：
* **是的，它们严格指向同一个物理地址**。在底层，它们共享同一个 Inode 编号，进而共享同一组存储数据的磁盘物理盘块。
---
### 2. FCB（目录项与 Inode）的特点
在现代文件系统中（FCB 拆分为“目录项”与“Inode”）：
* **目录项（dentry）层面**：有 **2 个独立的目录项**。
* 目录项 1：`文件名: "a" | Inode编号: 100`
* 目录项 2：`文件名: "b" | Inode编号: 100`
* **索引节点（Inode）层面**：全局**只有 1 个 Inode 实体**（编号 100）。
* 该 Inode 中的**硬链接计数（Link Count）为 2**。
---
### 3. 两个进程分别打开 `a` 和 `b` 时，计数值怎么变？
这里涉及两个不同的计数值：
1. **链接计数（`i_nlink`，硬链接数，磁盘/内存 Inode 中）**：
* **保持为 2，完全不变**。
* 打开文件不会增加硬链接数，只有执行 `ln` 创建新链接或 `rm` 删除文件时它才会变。
2. **访问计数（`i_count`，引用计数，内存 Inode 中）**：
* 进程 1 打开 `a`：系统把 Inode 100 读入内存，`i_count` 变为 **1**。
* 进程 2 打开 `b`：系统发现 Inode 100 已在内存，直接复用，`i_count` 累加变为 **2**。
---
### 4. 是一次还是两次读操作（磁盘 I/O）？
这取决于读取的是**元数据（目录/Inode）**还是**文件数据（Data Block）**：
#### ① 检索与打开阶段（`open`）
* **查目录项**：需要分别查找 `a` 和 `b` 所在的目录块（**2 次目录检索**）。
* **读 Inode**：
* 进程 1 打开 `a`：发起 **1 次磁盘 I/O** 将 Inode 读入内存。
* 进程 2 打开 `b`：直接命中内存中已存在的内存 Inode，**0 次磁盘 Inode I/O**。
#### ② 读取文件数据阶段（`read`）
* 如果进程 1 读取了该文件数据块，数据会被缓存在内核的页缓存（Page Cache）中。
* 紧接着进程 2 读取相同内容时，会直接从内核缓存中读取，**只需 1 次物理磁盘数据 I/O**（第二次由内存缓存直接满足）。
* 若没有缓存或两者读取互不重叠的未缓存盘块，则各自发起对应的磁盘 I/O。

## 十一、n个进程打开文件和n个进程共享文件
可以整理成考试版：
① n 个进程分别 open 同一个文件
    进程A打开文件表        系统打开文件表
    fd=3 ───────────────→ 表项① ──→ inode X
    进程B打开文件表
    fd=3 ───────────────→ 表项② ──→ inode X
    进程C打开文件表
    fd=4 ───────────────→ 表项③ ──→ inode X
因此：
- 系统打开文件表：有 n 个打开文件表项
- 每个进程的打开文件表：各有一个表项
- 每个进程的 FD 可以相同，也可以不同
- n 个系统打开文件表项的 inode 指向同一个文件
- 但每个系统打开文件表项的当前文件偏移量独立
---
② n 个进程共享同一个打开文件实例
例如 fork() 后：
    进程A打开文件表
    fd=3 ─────┐
              │
    进程B打开文件表       系统打开文件表
    fd=3 ─────┼──────→  表项① ──→ inode X
              │           offset=100
    进程C打开文件表       ↑
    fd=4 ─────┘           │
因此：
- 系统打开文件表：只有 1 个对应的打开文件表项
- 每个进程的打开文件表：各有一个表项
- 这些 FD 可以相同，也可以不同
- 这些 FD 都指向同一个系统打开文件表项
- 该表项再通过 inode 指向同一个文件
- 因此它们共享文件偏移量等打开状态
---
最核心的区别
你可以直接记这个：
分别 open：n 个进程 → n 个系统打开文件表项 → 同一个 inode。
共享打开实例：n 个进程 → 1 个系统打开文件表项 → 同一个 inode。

## 十二、文件存储空间管理

常用的空闲空间管理方法有：空闲表法、空闲链表法、位示图法、成组链接法。

### 成组链接法

算法原理：
1. 假设现在有 300 个盘块，然后每一百块分一组。
2. 那就是 1 到 100、101 到 200、201 到 300 三组。
3. 初始化时，1 号盘块存储 101 到 200 的编号，101 号盘块存储 201 到 300 的编号。
4. 然后超级块只放置 1 到 100 的信息，然后使用。
5. 当这一百个使用完了之后，就将 1 号盘块里存储的块全部读取出来，然后使用这 101 到 200 的信息。
6. 当发生退还的时候，它只执行两个判断：一是要么直接塞进超级块，二是要么把超级块打包给它当组长。
   - 所以当现在超级块里装着 101 到 200 的剩余名单时，如果 1 到 100 中发生了退还（比如 55、88），55 和 88 的编号就直接登记进超级块，跟里面的 101 到 200 的编号混在一起排队，盘块的编号顺序彻底打乱。

核心判断：
1. 超级块是一个「只看当前、不问过去」的后进先出（LIFO）栈。
2. 盘块类似于内存的页（4KB），然后超级组使用指针进行管理。

### 位示图法

位示图写成二维的，是因为总线的条数关系，让一行只能放 32 个盘块的信息。

### 与其他算法的关系

文件存储空间管理的算法，跟内存管理的那些算法很像。
