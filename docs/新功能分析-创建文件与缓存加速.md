## 二、功能一：创建文件 / 文件夹

### 2.1 现状分析

后端**目前完全没有增删能力**：
- `tree.py` 只有 `list_dir`（读目录），没有 mkdir/create
- `main.py` 的路由只有 `GET tree`、`GET/PUT file`、`GET raw`、`GET/PUT progress`、`GET search`
- 没有 `POST` 创建、`DELETE` 删除、`rename` 重命名的任何接口

**结论**：这是**纯新增**，后端加几个接口 + 前端加 UI，改动可控。

### 2.2 技术方案

核心是后端加三个接口，复用现有的 `safe_resolve` 做路径安全校验：

```
POST   /api/tree/{path}        创建文件夹（body: {name}）
POST   /api/file/{path}        创建文件（body: {name, content?}）
DELETE /api/tree/{path}        删除文件或文件夹（可选，第一版可先不做）
```

**后端实现要点**（`service/tree.py` 或新建 `service/fs.py`）：

| 操作 | 逻辑 |
|------|------|
| 建文件夹 | `safe_resolve(parent_path)` → `target = root/name` → `target.mkdir()`；已存在则报错「已存在」 |
| 建文件 | `safe_resolve` 校验父目录 → 校验后缀在 `EDITABLE_EXTS` → `write_text('')` 或初始内容 |
| 防冲突 | 名字已存在时返回 409/400，前端提示；**不要静默覆盖** |

**关键安全点**：
- 文件名/目录名要**清洗**：拒绝 `..`、`/`、`\`、空名、以及 `.` 开头（因为 `.md-reader-progress.json` 这类隐藏文件会被 `IGNORE_PREFIXES` 过滤，新文件若以 `.` 开头会「建了但看不到」）
- 复用 `safe_resolve` 保证不越出挂载目录
- 创建后返回新节点的结构，前端直接刷新对应目录

### 2.3 前端方案

在 `FileTree.vue` 加 UI 入口：

1. **每个目录行的「+」按钮**（hover 显示），点击弹出创建菜单：新建文件 / 新建文件夹
2. 弹出一个输入框（或 inline input），输入名字
3. 调用后端接口 → 成功后**局部刷新**该目录（重新 `getTree(path)`），不用整棵树刷新
4. 建文件后，可选：直接打开这个新文件进入编辑态

**交互细节**：
- 新建文件夹 → 刷新目录树即可
- 新建 md 文件 → 建一个空的 md，然后自动 `openFile` 进入编辑态，用户直接写内容

### 2.4 可选增强（第二版）

- **删除**：`DELETE /api/tree/{path}`，配合二次确认弹窗（危险操作）
- **重命名**：`PUT /api/tree/rename`
- **上传**：POST 上传 md/pdf/图片到指定目录

## 三、功能二：md 文档缓存加速

### 3.1 先纠正一个技术点：不是「cookie」

你提到「缓存到浏览器 cookie」，这里有个**关键的技术误区**需要先讲清楚：

| 存储 | 容量上限 | 适合存什么 | 结论 |
|------|---------|-----------|------|
| **Cookie** | 单条 4KB，总 4KB~几 MB，**每次请求都会自动带上** | 存 session token、登录态这种小块数据 | ❌ **完全不适合存文档内容** |
| **localStorage** | 约 5~10MB | 小块配置、简单缓存 | ⚠️ 能存但容量小，大文档会爆 |
| **IndexedDB** | 几百 MB~GB 级 | 大量结构化/二进制数据 | ✅ 适合但实现复杂 |
| **HTTP 缓存（ETag）+ 条件请求** | 由浏览器自动管理 | 文件内容缓存 | ✅✅ **最推荐** |

你的笔记是**文本 md**，单篇几百 KB，总量可能几十 MB。正确的做法是：

> **用 HTTP 缓存 + ETag 条件请求**：浏览器第一次打开文件时缓存下来，下次请求时带 `If-None-Match` 问服务器「文件变了吗」，没变服务器直接回 `304 Not Modified`（**响应体为空，几乎零流量**），浏览器就用本地缓存。

这**完全能实现**，而且是 HTTP 标准做法，不用自己造轮子。

### 3.2 技术方案（核心决策）

**方案 A：ETag + 304 条件请求（推荐）**

原理：
1. 后端 `GET /api/file/{path}` 返回内容时，同时返回 `ETag`（文件内容/修改时间的哈希，如 `mtime` 或 `md5`）
2. 浏览器（或前端 axios）缓存响应
3. 下次请求同一文件，自动带 `If-None-Match: <etag>`
4. 后端比对：文件没变 → 返回 `304 Not Modified`（空 body），前端直接用缓存
5. 文件变了 → 返回新内容 + 新 ETag

**优点**：
- 标准做法，浏览器原生支持，几乎零自定义代码
- 秒开：304 响应只有几十字节，比传输整个文档快几个数量级
- 自动失效：文件一改，ETag 变，缓存自动失效，**不会读到旧内容**
- 对 PDF、图片同样生效（`/api/file/raw` 也能加 ETag）

**缺点**：
- 缓存由浏览器管理，开发者控制粒度略低（但对我们够用）
- 需要处理「离线也能读」的场景的话，得配合 Cache API 或 Service Worker

**方案 B：前端手动缓存到 IndexedDB（更彻底）**

原理：前端读文件后存 IndexedDB，下次先读本地再异步校验云端。

**优点**：离线也能读、控制粒度细。

**缺点**：
- 实现复杂（要自己管缓存键、失效、版本）
- 对「只有你 + 手机 + 电脑」的场景**过度设计**
- 你的场景始终在线（访问的是部署的服务器），离线需求不强

**推荐方案 A**，理由：你的核心诉求是「打开快」，ETag 方案恰好用最少的代码实现「没变就秒开、变了自动更新」，不需要自己维护缓存逻辑。

> 补充：如果后面想要「弱网/离线也能打开上次读过的文档」，再上方案 B（IndexedDB），两者可以叠加。第一版建议只做方案 A。

### 3.3 后端改动（方案 A）

核心是给 `GET /api/file/{path}` 加 ETag：

```python
import hashlib

def file_etag(relative_path: str) -> str:
    """用文件 mtime + size 生成轻量 ETag（不用读全文件算 md5，更快）。"""
    target = safe_resolve(relative_path)
    stat = target.stat()
    return f'"{stat.st_mtime_ns}-{stat.st_size}"'

@app.get("/api/file/{path:path}")
def get_file(path: str, request: Request, response: Response):
    content = file.read_file(path)
    etag = file_etag(path)
    # 客户端带了 If-None-Match 且匹配 → 返回 304
    if request.headers.get("If-None-Match") == etag:
        response.status_code = 304
        return response
    response.headers["ETag"] = etag
    response.headers["Cache-Control"] = "no-cache"   # 每次都校验，但命中走 304
    return {"path": path, "content": content}
```

关键点：
- **ETag 用 `mtime + size`** 而非全文件 md5：文件一大，md5 要读全文件反而慢。mtime+size 对「改没改」的判断足够，且生成几乎零成本。
- **`Cache-Control: no-cache`**（不是 no-store）：意思是「可以缓存，但每次用前都要先问服务器校验」，这正是我们要的行为。
- 保存文件时 `write_file` 会自动更新 mtime，ETag 随之变化，缓存自动失效。

> 注意：`/api/file/raw/{path}`（PDF/图片）也可以同样加 ETag，浏览器对 `<img>`、pdf.js 的 fetch 都会自动带条件请求。第一版可选，建议一起做。

### 3.4 前端改动（方案 A）

**关键点：axios 默认不会自动缓存 GET，但会正确处理 304。**

其实前端要做的很少，因为：
- 如果直接让浏览器原生请求（如 `<img src>`、fetch），浏览器**自动**处理 ETag/304 缓存，前端零代码
- 但当前用 axios 发请求，需要确认 axios 对 304 的处理

具体做法：

1. **对 md 文件**：由于内容要进 Vue 的 `fileContent`，仍走 axios。让 axios 正确处理 304：
   - axios 默认对 304 会走错误分支或返回空。需要在拦截器里处理：`res.status === 304` 时视为成功，内容用前端自己的缓存。
   - 更简单的方式：**前端加一层轻量内存缓存**（一个 `Map<path, {content, etag}>`），配合 axios 的 `If-None-Match` 手动头，命中 304 就用内存里的 content。

2. **对 PDF/图片**：`/api/file/raw` 走原生 `fetch` / `<img>`，浏览器自动缓存，**前端完全不用管**。

**推荐的最简实现**（md 部分）：

```js
// api 层加一个带 ETag 的 getFile
const fileCache = new Map()  // path -> { content, etag }

async function getFileCached(path) {
  const cached = fileCache.get(path)
  const headers = cached?.etag ? { 'If-None-Match': cached.etag } : {}
  try {
    const res = await http.get(`/api/file/${encodePath(path)}`, { headers })
    // 200：新内容，更新缓存
    fileCache.set(path, { content: res.data.content, etag: res.headers['etag'] })
    return res.data.content
  } catch (err) {
    // 304：axios 会抛错（status 304 不在 2xx）
    if (err.response?.status === 304 && cached) {
      return cached.content   // 直接用缓存
    }
    throw err
  }
}
```

> 更优雅的做法是拦截 axios 让 304 不抛错（`validateStatus: s => s < 500`），再统一处理。上面是最小可用的示意。

### 3.5 缓存效果预估

| 场景 | 首次打开 | 再次打开（未改） | 再次打开（已改） |
|------|---------|-----------------|-----------------|
| 网络传输 | 全文（如 50KB） | **~0**（304 空响应） | 全文 |
| 耗时 | 数百 ms~秒 | **几 ms~几十 ms** | 同首次 |
| 内容 | 正确 | 正确（本地缓存） | 正确（新内容） |

对「只有你 + 手机 + 电脑」的使用场景，这个加速非常明显——绝大多数打开都是「没改过的文档」，直接命中 304 秒开。

### 3.6 需要注意的边界

1. **多设备同步**：你在电脑上改了文件，手机上缓存的是旧 ETag，下次打开会拿新内容（因为 ETag 变了走 200）。**不会读到旧内容**，这正是 ETag 的好处。
2. **`no-cache` vs `max-age`**：用 `no-cache` 是「每次校验」，最安全。如果觉得校验请求都嫌多，可以 `max-age=60`（1 分钟内直接读缓存不校验），但建议先用 no-cache 保证正确性。
3. **进度记忆已存后端**：阅读进度本身已经走后端了（上一轮做的），和内容缓存不冲突。

## 六、需要你确认的决策点

1. **删除功能**要不要第一版就做？（我建议先只做「创建」，删除/重命名放第二版，因为删除是危险操作需要额外小心）
2. **缓存方案**确认用 ETag + 304（方案 A）？还是你想要更彻底的 IndexedDB 离线缓存（方案 B，更复杂但能离线读）？
3. **ETag 精度**：用「mtime+size」判断（快，但同一毫秒内改两次同大小可能漏判）还是「md5 全内容」判断（绝对准，但大文件算哈希有开销）？我推荐 mtime+size，对笔记场景足够。
4. **缓存有效期**：`no-cache`（每次校验，最安全）还是 `max-age=60`（1 分钟内有小概率读旧）？我推荐 no-cache。

### 实际落地要点
- 创建接口：`POST /api/tree/{path}`（文件夹）、`POST /api/file/{path}`（文件，仅 md/txt）。
- 名称清洗：拒绝 `.` 开头（防隐藏文件）、`..`、`/ \ : * ? " < > |`，复用 `safe_resolve` 防穿越。
- 前端：目录行 hover 显示「+」，根目录有「新建」按钮；新建文件后自动进入编辑态。
- ETag：`mtime_ns + size` 生成，`/api/file` 和 `/api/file/raw`（PDF/图片）都加了。
- 前端 axios 需 `validateStatus` 放行 304，`getFile` 用内存 Map 缓存 + `If-None-Match` 头，命中 304 直接用缓存。

### 遇到的坑
1. **axios 默认把 304 当错误**：必须 `validateStatus: s => (s>=200 && s<300) || s===304`，否则 304 走 error 分支。
2. **FastAPI 返回 304**：直接 `response.status_code = 304; return response`（空 body）。
3. **ETag 精度选型**：mtime+size 比 md5 快得多，且写文件 mtime 自动更新，缓存自动失效。
