# 新增功能分析：PDF 阅读 + 阅读位置记忆

> 本文档分析两个新功能的可行性、技术选型和实现方案，供评估确认后再动手写代码。

---

## 一、需求概述

| # | 功能 | 目标 |
|---|------|------|
| 1 | **PDF 阅读** | 在阅读器中直接打开 `.pdf` 文件，翻页阅读，与 md 阅读体验一致 |
| 2 | **阅读位置记忆** | 记住每个文件上次读到哪，下次打开自动回到那个位置 |

---

## 二、功能一：PDF 阅读

### 2.1 现状分析

当前系统只处理文本文件（`.md` / `.markdown` / `.txt`）：
- 后端 `file.py` 用 `read_text()` 读文本，`PDF` 是二进制文件，直接读会乱码
- 前端 `MarkdownView` 只渲染 md，没有 PDF 渲染能力
- `config.py` 的 `EDITABLE_EXTS` / `SEARCHABLE_EXTS` 都不含 `.pdf`
- 目录树 `tree.py` 会显示所有文件，但 `.pdf` 目前点开是「不支持预览」

**结论**：PDF 阅读是**新增能力**，需要后端 + 前端配合，但改动可控。

### 2.2 技术选型（核心决策）

有 3 种方案，各有取舍：

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **A. pdf.js 前端渲染**（推荐） | 前端用 Mozilla pdf.js 解析 PDF 二进制，渲染到 canvas | 体验好、翻页流畅、缩放/搜索/大纲都支持；后端只负责"把文件字节发出来" | 前端引入 pdf.js（~几百 KB）；旧浏览器兼容性略差 |
| **B. 后端转图片** | 后端用 PyMuPDF 把每页转成 PNG，前端像看图片一样翻页 | 前端简单，无需 pdf.js | 需要 Python 依赖（PyMuPDF ~50MB），大 PDF 转图慢，缩放体验差 |
| **C. 浏览器原生 iframe** | 直接 `<iframe src="xxx.pdf">` 交给浏览器内置 PDF 查看器 | 零前端代码 | 各浏览器/手机端体验不一致，无法控制样式和进度记录，手机上很不可靠 |

**推荐方案 A（pdf.js）**，理由：
1. 与现有「前端渲染 + 后端读文件」架构完全契合，后端只需加一个「按字节返回文件」的接口
2. 体验最好，且能拿到「当前页码」用于进度记忆（与功能二联动）
3. 纯前端库，不增加 Python 依赖，Docker 镜像体积几乎不变

### 2.3 后端改动

新增一个「读二进制文件」的接口（现有 `/api/file` 只返回文本）：

```
GET /api/file/raw/{path}     → 返回文件的原始字节（PDF、图片等二进制文件）
```

关键实现点：
- 复用 `path_util.safe_resolve` 做路径安全校验（防穿越）
- 用 `FileResponse` 或 `Response(content=bytes)` 返回，设置正确的 `Content-Type: application/pdf`
- 顺带解决 **md 里引用的本地图片**（`notes/` 目录里有 `assets/*.png`，md 里 `![](assets/xxx.png)` 目前会裂图）——同一个接口就能让图片显示

### 2.4 前端改动

1. **新增 `PdfViewer.vue` 组件**，用 pdf.js 渲染：
   - 加载 PDF → 逐页渲染到 canvas
   - 翻页（上一页/下一页/页码跳转）
   - 缩放（+/-/适应宽度）
   - 记录当前页码 → 上报给进度记忆

2. **`App.vue` 根据文件扩展名分发**：
   ```
   .md / .markdown / .txt  → MarkdownView（现有）
   .pdf                    → PdfViewer（新增）
   图片(.png/.jpg)          → 直接 <img> 展示（顺手支持）
   ```

3. **`FileTree.vue`**：`.pdf` 文件图标换成 📕/专门图标，设为可点击（`editable` 概念改为 `readable`，因为 pdf 只读不编辑）

4. **依赖**：`package.json` 加 `pdfjs-dist`

### 2.5 关键风险与注意

- **pdf.js 的 worker**：pdf.js 需要单独加载 worker 文件，Vite 里要配置 `?url` 导入，否则性能差/报错
- **大 PDF**：逐页懒加载（只渲染当前页），避免一次性渲染所有页卡死
- **移动端**：pdf.js 在手机上能用，但要注意 canvas 尺寸适配（用 `devicePixelRatio` 控制清晰度）
- **中文 PDF**：pdf.js 对中文字体支持良好，无需额外配置

## 三、功能二：阅读位置记忆

### 3.1 需求拆解

「记住上次读的位置」要区分两种文件类型，记录的内容不同：

| 文件类型 | 记录什么 | 恢复什么 |
|---------|---------|---------|
| md/txt | 滚动位置（scrollTop 或锚点标题） | 打开后滚动到那个位置 |
| pdf | 当前页码 | 打开后跳到那一页 |

### 3.2 存储方案（核心决策）

这是最关键的选择，直接影响跨设备体验：

| 方案 | 存储位置 | 优点 | 缺点 |
|------|---------|------|------|
| **A. 浏览器 localStorage** | 存在**当前设备**浏览器里 | 零后端改动，最简单 | 换设备/换浏览器就丢了；清理浏览器数据会丢 |
| **B. 后端持久化（JSON 文件）**（推荐） | 存在挂载目录下的一个 `.progress.json` | 跨设备同步（Docker 部署后手机/电脑共享进度）；随笔记目录一起备份 | 后端要加读写接口；需处理并发写 |

**推荐方案 B**，理由：
1. 你之前明确要「跨设备」——Docker 部署后，手机和电脑访问的是同一个服务，进度应该一致
2. 进度数据跟着笔记目录走（存在挂载目录里），备份笔记 = 备份进度
3. 实现也不复杂，就是一个「读/写一个小 JSON」的问题

> 补充：可以做「A+B 双保险」——后端持久化为主，前端 localStorage 做即时缓存（打开文件先读缓存秒回，再异步同步后端），但第一版建议先做纯 B，简单清晰。

### 3.3 数据格式

进度文件放在挂载根目录下（隐藏文件，`.md-reader-progress.json`）：

```json
{
  "操作系统整理/a.3内存管理/总文件.md": {
    "type": "md",
    "scrollTop": 4321,
    "updatedAt": 1759999999
  },
  "数据结构/2树/总文件.md": {
    "type": "md",
    "headingId": "三、树的遍历"    // 或者用标题锚点，比 scrollTop 更稳
  },
  "资料/教材.pdf": {
    "type": "pdf",
    "page": 42,
    "updatedAt": 1759999999
  }
}
```

**md 的进度记录选型**：
- 方案 1：记 `scrollTop` 像素值 —— 简单，但不同屏幕宽度下换行不同，位置会偏
- 方案 2：记**当前视口最顶部的标题锚点**（如「三、树的遍历」）—— 更稳，跨设备一致，因为锚点基于内容而非像素

**推荐方案 2（标题锚点）**，md 用「当前滚动位置对应的最近标题」做锚点，恢复时滚动到该标题。无标题时退化为 scrollTop 比例。

### 3.4 后端改动

新增两个轻量接口：

```
GET  /api/progress            → 读取全部进度（或按路径查单个）
PUT  /api/progress/{path}     → 保存某文件的进度
```

实现：
- 进度文件路径：`ROOT_DIR / ".md-reader-progress.json"`
- 用 `path_util.safe_resolve` 保证进度文件也在挂载目录内
- 读：文件不存在返回空 `{}`
- 写：读旧 JSON → 合并更新 → 写回（原子写，先写临时文件再 rename，防损坏）
- 并发：单用户场景用简单锁（或直接接受"最后写入生效"）

### 3.5 前端改动

1. **打开文件时**：请求进度 → 如果有记录，恢复位置
2. **滚动/翻页时**：**防抖**记录当前位置（避免频繁请求），离开页面/切换文件/定时（如每 3 秒）上报
3. **md 恢复逻辑**：渲染完成后，找到锚点标题，`scrollIntoView`；无锚点则按 scrollTop 比例滚动
4. **pdf 恢复逻辑**：直接跳转到记录的页码

### 3.6 触发时机（防抖策略）

- 滚动时 `debounce(500ms)` 更新内存中的进度
- 切换文件 / 关闭标签页（`beforeunload`）/ 定时（5 秒）才真正发请求保存
- 避免「滚动一次就发一次网络请求」的性能问题

## 六、需要你确认的决策点

1. **PDF 渲染方案**：确认用 pdf.js（方案 A）？还是你想要后端转图（方案 B）？
2. **进度存储**：确认用后端持久化（方案 B，跨设备同步）？还是只存本地浏览器（方案 A，简单）？
3. **进度文件位置**：进度数据放在挂载目录下（`.md-reader-progress.json`，会出现在你的笔记文件夹里）可以接受吗？还是想存到别的地方？
4. **md 进度精度**：用「标题锚点」还是「像素位置」？（我推荐标题锚点，跨设备更准）
5. **顺带功能**：md 里引用的本地图片（你 `notes/` 里已经有 `assets/*.png` 了）要不要这次一起解决？这其实和 PDF 是同一个接口就能搞定。

## 七、工作量预估

- **后端**：小。两个接口 + 一个进度读写函数，约 1 小时量级
- **前端 PDF**：中。pdf.js 集成 + 翻页缩放，约半天量级
- **前端进度记忆**：小到中。锚点提取 + 恢复 + 防抖上报，约 2-3 小时量级
- **顺带图片显示**：很小。复用二进制接口

整体是一个「一到两天」的小迭代，不涉及架构重构。

### 实际落地时的额外决策/调整
- 图片是 md 里的**相对路径**（相对于 md 文件所在目录），`renderMarkdown(content, baseDir)` 增加 baseDir 参数做路径重写。
- 顺带支持了**图片文件的直接查看**（`ImageViewer.vue`，点目录树里的 png/jpg 直接预览）。
- 进度上报用 `beforeunload` + `navigator.sendBeacon`（POST），所以进度接口同时接受 PUT 和 POST。
- 文件类型判断从 `editable` 扩展为 `readable`（含 pdf、图片），编辑按钮只对 md/txt 显示。

### 遇到的关键坑
1. **FastAPI 路由顺序**：`/api/file/{path:path}` 会贪婪匹配 `/api/file/raw/xxx`，raw 接口必须定义在 file 接口之前，否则永远 404。
2. **sendBeacon 只支持 POST**，不能发 PUT。
